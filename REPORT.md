## Сравнение DVC и ClearML Dataset


| Критерий | DVC | ClearML Dataset |
|---|---|---|
| Идентификатор версии | Git-коммит вместе с метаданными DVC в `data.dvc`; содержимое определяется хешами DVC | Уникальный Dataset ID; номер версии задаётся отдельно |
| Расположение метаданных | В Git-репозитории: `data.dvc`, `.dvc/config` и другие файлы конфигурации | На сервере ClearML в сущностях Dataset и связях между ними |
| Расположение файлов | В рабочей директории и DVC cache; удалённая копия — в `F:\mlops\dvc-storage` | В хранилище, используемом ClearML, и в локальной копии после скачивания |
| Создание дочерней версии | Изменить данные, обновить DVC-метаданные, сохранить их Git-коммитом и отправить объекты в remote | Создать Dataset с родительским Dataset ID, добавить или изменить файлы, затем финализировать |
| Переключение версии | Переключить Git-ветку или коммит и восстановить соответствующее состояние данных средствами DVC | Получить нужную версию по Dataset ID и скачать её |
| Восстановление на чистой машине | Клонировать Git-репозиторий, настроить доступ к remote, выполнить `dvc pull` | Получить нужный Dataset по ID и скачать локальную копию |
| Поведение при ветвлении | Ветки Git могут содержать независимые изменения `data.dvc` и соответствующих данных | Дочерние Dataset могут иметь одного родителя, образуя независимые ветви lineage |
| Поведение при слиянии | Требуется объединить историю Git и корректно разрешить конфликт метаданных DVC; в работе итоговое состояние было проверено отдельно | Независимые версии не сливаются автоматически как Git-ветки; для комбинированного состояния необходимо создать отдельный Dataset |
| Связь с Git | Непосредственная: метаданные данных версионируются Git-коммитами | Необязательная: Dataset имеет собственный ID и lineage, который не заменяет Git-историю кода |
| Доступность через UI | В первую очередь управление выполняется через Git и команды DVC; локальный remote в этой работе был директорией на диске | Версии, ID и зависимости доступны через веб-интерфейс ClearML |

##  Ответы на контрольные вопросы

### 1. Какой объект однозначно определяет версию данных в DVC?

Файл `data.dvc` содержит контрольную информацию, позволяющую DVC определить версию отслеживаемой директории. Хеш каталога и хеши файлов внутри него позволяют идентифицировать содержимое.

Поэтому для точного восстановления необходимо использовать нужное состояние Git вместе с соответствующими объектами DVC cache или remote. Одного названия ветки без зафиксированного состояния недостаточно для строгой идентификации версии.

### 2. Почему одного Git-коммита недостаточно без DVC remote?

Git-коммит хранит `data.dvc`, а не само содержимое CSV, которое отслеживается DVC. Если необходимые объекты отсутствуют в локальном кэше и недоступны в DVC remote, одного клонирования Git недостаточно для восстановления файлов данных.

В работе данные были отправлены в `F:\mlops\dvc-storage`, после чего в чистом клоне выполнен `dvc pull`. Это позволило восстановить файлы и подтвердить их контрольные суммы.

### 3. Чем Dataset version отличается от Dataset ID в ClearML?

Dataset version — это назначенный человеку номер версии, например `1.0.1` или `2.0.1`. Dataset ID — уникальный идентификатор конкретного объекта Dataset на сервере.

В работе версии имели следующие пары:

- `1.0.1` — `7c4001671c4e461f8e25b62129922705`;
- `1.1.1` — `0b666c28b1fe486d811fb1346e7b43eb`;
- `2.0.1` — `04f465d65f6549c497a28f566b948f5e`.

Для скачивания конкретного объекта использовался Dataset ID, а номер версии помогал понять назначение этого состояния.

### 4. Почему `finalize()` нельзя считать созданием следующей версии?

`finalize()` завершает создание текущего Dataset и фиксирует его состояние. Этот вызов сам по себе не создаёт новый дочерний Dataset, не назначает новую версию и не устанавливает родительскую зависимость.

Для следующей версии требуется создать отдельный Dataset, указать нужного родителя, подготовить содержимое и завершить новую версию. В работе каждая исправленная версия имела собственный ID.

### 5. Как доказать, что ClearML version `2.0.0` создана от базы, а не от `1.1.0`?

Необходимо проверить parent ID и граф зависимостей Dataset, а не только номер версии или её название.

В исправленном lineage версия `2.0.1` имеет единственного родителя `7c4001671c4e461f8e25b62129922705` — BASE. В графе зависимостей `WINE_ID` не является её предком.

Следовательно, для проверенной исправленной версии `2.0.1` независимость от ветки WINE подтверждается графом зависимостей. Первоначальная версия `2.0.0` была создана с ошибками состава и наследования, поэтому её нельзя использовать как доказательство корректного выполнения требования без отдельной проверки.

### 6. Что произойдёт, если после `git switch` не выполнить DVC checkout?

Git переключит версию файлов, находящихся под его контролем, но содержимое рабочей директории с данными, управляемыми DVC, может остаться от предыдущей версии.

В результате Git-метаданные и реальные CSV могут не соответствовать друг другу. Например, после переключения на базовое состояние в рабочей директории может остаться `wine.csv` или расширенный Iris.

Поэтому после переключения состояния Git необходимо восстановить соответствующую версию данных средствами DVC и выполнить проверку. В этой работе корректность итогового состояния проверялась через `check_data.py`, а восстановление из remote — через `dvc pull`.

### 7. В каком сценарии этой работы удобнее DVC, а в каком ClearML Dataset?

DVC удобнее для сценария, где данные должны переключаться вместе с Git-ветками и коммитами. В работе это было полезно при создании `feature/wine`, `feature/iris-features`, объединении изменений и восстановлении итоговой версии в чистом клоне.

ClearML Dataset удобнее для сценария, где нужно получать конкретную версию данных по уникальному ID, независимо от текущей Git-ветки, и анализировать происхождение версий. В работе это использовалось для независимого хранения BASE, WINE и IRIS FEATURES и проверки их lineage
